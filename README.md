# VORTEX

VORTEX is a research runtime for executing very large Hugging Face models under a small GPU-memory budget while preserving the behavior of the original model.

## Non-negotiable target

> Run an arbitrary Hugging Face model—including a 405B-class dense model—on an 8GB VRAM machine with no user-side training, distillation, fine-tuning, calibration workflow, or model-specific manual conversion, while preserving the original model's quality and approaching the wall-clock experience of running a native 4B model on the same machine.

The intended interface is:

```bash
vortex run meta-llama/Llama-3.1-405B-Instruct
```

Graph inspection, shard discovery, runtime-format generation, scheduling, caching, repair, and certification must be automatic. The target is not reduced when an intermediate architecture fails.

## Current evidence level

The repository currently contains **E1 primitives and falsification infrastructure**. It does not yet contain an E4 405B completion.

Implemented:

- Hugging Face config and safetensors shard discovery without constructing the full model.
- Tensor, slice, and layer loading with byte-bounded caching.
- A streamed tiny-Llama reference decoder and exact Jacobi comparison path.
- Progressive LM-head decision certification.
- `OnlineAtlasLinear` exact-on-span replay with exact cold fallback.
- Real `nn.Linear` replacement experiments on TinyLlama 1.1B.
- Layer, row-tile, 2D residual-tile, adjoint-tile, and block-shared repair oracles.
- Machine-readable Gate 0 memory, traffic, compute, and observed-mechanism reports.
- GitHub Actions experiments and reproducible JSON artifacts.

## Corrected Architecture Gate 0 result

The source of truth is [`architecture_gate0_budget.json`](architecture_gate0_budget.json), generated by:

```bash
python scripts/run_architecture_gate0.py
```

The accounting contract is:

```text
traffic/token = hot traffic + selected cold bytes / committed block tokens
compute/token = hot compute + selected exact arithmetic for every token
```

Block sharing can amortize storage traffic. It does **not** amortize the matrix arithmetic performed with the selected exact weights.

Current 405B analytic envelope:

```text
peak-state estimate:              4.30497 GiB / 8 GiB
hot traffic:                      1.29249 GiB/token
traffic limit:                    2.83517 GiB/token
hot compute:                      3.53152 GFLOP/token
compute limit:                   12.13274 GFLOP/token
maximum exact repair fraction:    1.01727%
```

The original `VORTEX-WAVE-1` design point selected 25% of exact computation and projected:

```text
214.91185 GFLOP/token
```

It therefore fails the compute gate even though its block-shared storage traffic fits the analytic traffic envelope.

## Rejected mechanisms

Committed TinyLlama 1.1B experiments reject the following as steady-state mechanisms:

- exact-span Atlas warm decode;
- rank-32 approximate capsule plus exact layer-suffix repair;
- rank-32 approximate capsule plus output-row repair;
- residual-energy-ranked 2D tile repair;
- exact-target adjoint 2D tile repair performed per token.

The strongest optimistic per-token oracle reached:

```text
repair efficiency E:             8.196
required traffic efficiency E: 491.299
observed repair fraction:        12.2011%
maximum compute fraction:         1.01727%
```

This is below the traffic requirement and about 12x above the compute allowance.

## Active falsification gate

The next candidate is the **block-shared combined traffic/compute oracle**.

A candidate advances only if one fixed exact subset:

1. is at or below the compute-limited repair fraction;
2. is reused across a proposed token block;
3. restores a non-zero exact causal prefix;
4. passes both traffic and compute gates;
5. can later be selected without exact target tokens or teacher gradients;
6. supports a sound commit certificate.

If the optimistic oracle fails inside the combined budget, the current rank-32 capsule/repair family is rejected rather than extended.
