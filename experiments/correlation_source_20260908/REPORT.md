## 3. 실제 생성기: 공동 패턴으로 비선형 결합을 계산한다

N개 위치에 k비트 값 `p_j=(X_1[j],...,X_k[j])`가 있다고 하자. 질의는 행 마스크 r와 열 마스크 u로 정하는 `q_ij=r_i u_j`다. 부모 함수 f는 k비트의 임의 Boolean 함수이며, 코드에서는 실제 ANF 단항식 목록으로 제공한다. 목록이 큰 함수의 비용도 없애주지 않는다.

원본의 서로 다른 패턴들을 정렬하여 `p^(1),...,p^(R)`로 저장하고, 각 위치에 어떤 패턴이 있는지를 폭 `ell=ceil(log2 R)`의 ID로 기록한다. 가능한 입력의 정답표를 만들거나 2^k 패턴 전체를 열거하지 않는다. 원본에서 실제 나타난 패턴만 저장하지만, 원본 N개 값은 준비 때 모두 읽는다.

현재 질의에서 다음 수를 생성한다.

`c_a = sum_{j : p_j=p^(a)} q_j`.

그러면 정확한 답은 다음이다.

`XOR_j q_j f(p_j) = XOR_a ((c_a mod 2) AND f(p^(a)))`.

증명: 각 위치는 정확히 하나의 패턴 집합에 속한다. 같은 패턴에서 f의 값은 같으므로 XOR에 홀수 번 기여하는 집합만 남는다. 이 분할 항등식은 임의 k, 원본 값, 마스크, Boolean f에 대해 성립한다. 검사 자료에서만 우연히 맞는 관계가 아니다. 다만 **그 개수를 저렴하게 생성한다는 정리는 아니다.**

구현은 현재 마스크가 선택한 모든 위치에서 ID를 읽고 해당 개수를 증가시킨다. 그 다음 홀수 개수의 패턴을 읽어 모든 제공된 단항식을 평가한다. 원본 자식 배열을 질의 객체에 넘기지 않지만, 그 정보는 위치 ID와 패턴 사전에 남아 있다. 전체 직렬화 바이트열은 현재 구현에서 호스트 RAM에 올라와 있다. SSD 적응 읽기나 GPU 배치를 구현한 것이 아니다.

### 기존의 누락 정보를 실제로 복구

두 위치의 공동 패턴이 `[00,11]`인 경우와 `[01,10]`인 경우를 비교한다. 자식 둘의 XOR 답은 모두 `[1,1]`이지만, 각 위치에 AND를 적용한 뒤 XOR한 부모 답은 각각 1과 0이다. 이 반례는 기존 인계에 있던 것으로 새 발견이 아니다.

이번 생성기는 두 원본의 공동 패턴 개수를 직접 만들어 각각 올바른 부모 값을 돌려준다. 따라서 누락된 교차 정보에 이름만 붙인 것이 아니라, 그 정보를 생성하고 사용하는 실행 절차까지 있다. 그러나 정보를 생성할 때 선택 위치 전체를 방문하는 비용이 남는다.

## 4. 유한 실행·저장·시간 계산

직렬화 크기는 정확히 다음과 같다.

`D = 64 + R*ceil(k/8) + ceil(N*ell/8)` 바이트.

64바이트는 32바이트 헤더와 32바이트 무결성 다이제스트다. 로더는 전체 다이제스트와 모든 ID의 범위를 검사한다. 이 비용은 로딩 비용이며 공짜가 아니다. 해시는 전송 오류 검사이고 악의적으로 바뀐 원본에 대한 수학적 인증서가 아니다.

생성기는 입력 검사, 비교 정렬, 패턴 중복 제거, N번의 이진 검색, ID 비트 포장, 전체 파일 해싱 순서로 종료한다. O(N log N)개의 k비트 비교와 O(N ell) 비트 포장, 원본·정렬 목록·ID 목록·직렬화 버퍼의 저장이 필요하다. 원본 체크포인트는 보존되며 생성 파일 크기를 원본 대체 총비용이라고 세지 않는다.

질의의 선택 위치 수를 Q, 부모 함수 수를 F, 전체 단항식 수를 L이라고 하자. 본 구현은 다음을 수행한다.

1. 질의와 함수 범위를 검사하고 R개 개수와 F개 출력을 0으로 초기화한다.
2. 행·열 마스크를 검사한다. Q개의 ID를 읽고 Q번 개수를 갱신한다.
3. R개 개수를 훑고 홀수인 패턴 A개를 읽는다. `A<=min(R,Q)`이다.
4. A번마다 실제 L개 단항식을 평가하고 F개 출력 XOR를 수행한다.

ID 필드와 패턴 데이터에 대한 논리적 읽기 상한은 `Q*ceil((ell+7)/8)+min(R,Q)*ceil(k/8)` 바이트다(ell=0에서는 ID 읽기 0). 마스크·개수의 읽기/쓰기·입력검사·출력·코드·주소·버퍼 할당은 이 식 밖의 추가 비용이다. 실제 계수기는 겹치는 바이트를 반복해서 읽으면 반복 참조로 센다. 캐시 미스, 물리 페이지 수, 지연과 동일하지 않다.

개수 하나에는 `ceil(log2(N+1))`비트면 충분하다. 다만 Python에서는 객체와 큰 정수 메모리가 추가된다. 현재 구현에는 수치적인 최악 할당 상한이나 하드웨어 서비스 시간 보장이 없다. 큰 정수 AND·비교·비트 시프트를 무조건 단일 명령으로 세지 않는다. `results/costs.json`은 비트 작업과 저장의 보수적인 점근 상한 및 빠진 기계상수를 명시한다. **전체 O4와 O5를 닫는 초 단위 상한이 아니다.**

### 목표 규모에 대한 이 표현의 판정

16비트 패턴이 65,536종류인 조건을 가정하면 위치 ID도 16비트다. 4050억 개 원본 값에 대응하는 ID만 810,000,000,000바이트, 약 754.371GiB다. 사전·헤더·원본 보존·임시 공간은 추가된다. 이는 실제 405B 패턴 분포를 측정한 결과가 아니라, **이 표현의 한 조건에 대한 유도값**이다. 큰 자료는 32비트 형식 필드를 넘지 않도록 분할해야 하므로 파일별 헤더도 더해진다.

패턴 수가 작으면 저장량이 작아질 수 있으나, 원본 전체에서 작은 패턴 수를 확보하는 방법은 증명하지 않았다. Q=N인 질의에서는 저장 형식이 어떻게 되든 이 구현이 N개 위치를 방문한다. 이것은 해당 구현의 비용이지 모든 적응형/비선형 자료구조의 하한이 아니다.

## 5. 결과를 본 뒤에도 남긴 대조와 후속 구성

사전 고정한 k=2,4,8,16; 4×4 위치; 씨드11,29; diverse/repeated/constant의 24개 원본을 사용했다. 모든 256개 행·열 마스크 쌍에서 단일 비트·모든 이차항·단일 비트 XOR 함수를 검사했다.

**6,144개 질의, 290,304개 출력 비트에서 불일치 0**이었다. 별도 파일 디코더와 각 단항식을 비트의 곱으로 평가하는 독립 검사도 실행했다. 이것은 이진 교차 질의이며, BF16 모델 실행 수가 아니다.

예를 들어 k16·씨드11·diverse의 원본은 32바이트이고 생성 파일은 104바이트다. 전체 위치 질의에서는 ID 16바이트와 패턴 32바이트를 논리적으로 읽고, 개수를 16번 갱신하며, 단항식 2,432개를 평가한다. 원래 packed 원본을 한 번 읽는 32바이트보다 적다고 할 수 없다. 반복 대조군은 홀수 패턴이 없어 함수 평가를 생략할 수 있었지만, 개수 생성용 위치 방문은 여전히 16번이었다.

### 원본 반올림 순서를 보존하는 후속 단계

공동 개수를 얻어도 원래 숫자 계산으로 바로 이어지지 않는다. 다음 두 항 순서는 같은 패턴·개수와 정확한 합 2를 갖는다.

`[2^24, 1, -2^24, 1]` / `[2^24, -2^24, 1, 1]`.

하지만 고정한 균형 FP32 합산 결과는 각각 1과 2다. 이 반례도 기존 결과의 회귀 검사이며 새 반례로 세지 않는다. 분수 기반 독립 반올림 구현으로도 비교했다. FP 연산의 괄호·FMA 구분은 NVIDIA 공식 자료 [S1]과 일치한다.

그래서 이번 소스의 **위치 ID를 원래 순서대로 읽어** 각 FP32 항을 복원하고, 원래 트리에서 더하는 후속 실행기를 구현했다. 두 사례 모두 정확하게 처리하지만, 네 항마다 ID 네 개·패턴 네 개를 읽고 원래 덧셈 세 번을 수행한다. 입력과 가중치에서 이 항들을 생성하는 비용도 필요하다. 이 실행기는 제한된 수치 증인의 검사기이지 일반적인 HF/CUDA 수치 커널이 아니다.

즉, A의 교차 정보 누락을 실제 생성으로 보완한 뒤 원본 순서까지 연결했지만, 후속 단계도 원래 소비 비용을 제거하지 못했다. 부분 XOR의 정확성을 전체 수치 실행의 정확성으로 확대하지 않는다.

## 6. 출력·RNG·다음 상태의 증명 의무

형식적으로, 원본 전이의 내부 연산을 동일한 입력에서 같은 **모든 관측 비트**를 반환하는 결정론적 절차로 교체하고, RNG의 호출·소비 순서와 외부 상태 쓰기 순서를 보존한다면, 각 대체 연산 이후 상태가 같다는 귀납법으로 전체 전이도 같다. 이것은 검증해야 할 접합 규칙이지, 이번에 전체 모델을 대체했다는 결과가 아니다.

이번 원시 함수는 RNG를 사용하지 않는다. 실험 원본을 만들 때의 `random.Random`은 모델 RNG와 무관하다. 원본 Transformer의 입력을 이 원시 함수의 질의로 바꾸는 저비용 변환, projection·SiLU·softmax·정규화의 전체 실행, KV 갱신과 원래 샘플러는 구현하지 않았다. 따라서 **원본 모델의 출력·RNG·다음 상태 보존 O3는 OPEN**이다. C 참조나 GPU를 실행하지도 않았다.

**전체 의무 중 새로 CLOSED 처리한 항목은 없다.**

다음 핵심 구성은 아래 인터페이스에 이름을 붙이는 것이 아니라, 이를 실제로 만족하는 새로운 알고리즘이어야 한다.

* 원본의 교차·순서 정보를 유지하는 저장 표현을 유한하게 생성한다.
* 현재 입력에서 전체 위치 ID나 모든 계수 곱을 먼저 만들지 않고 원본 수치 결과와 필요한 상태를 생산한다.
* 원본 대신 읽는 데이터·그 주소 생성·모든 복구 연산·준비 비용을 포함한 충분 상한으로 최소 10배 경로를 먼저 보인다. 그 뒤에도 최종 p50/p95에는 별도의 동일 머신 비교 증명이 필요하다.

아직 이 인터페이스의 통과 후보는 없다. 작은 코드 씨드, 패턴 사전의 크기, 부호화 이름만 바꾸는 탐색을 후속 핵심 작업으로 승인하지 않는다. B를 다시 선택한다면 먼저 native 연산의 공유 관계를 적은 표/회로로 **구성하는 규칙**을 제시해야 한다. C를 선택한다면 이미 실패한 전수 전이표 대신 원본에서 비열거 변환·출력 경로를 생성해야 한다. 작은 소거 폭·작은 상태·좋은 패턴을 미증명 가정으로 두면 CONDITIONAL을 넘지 못한다.
