# 압축된 실행 규칙의 크기와 질의 비용을 함께 검사한 결과

2026-09-06. 기준 저장소 `yjunhyuk920-ui/Vortex`, PR #129의 원격 커밋
`4a6d16487002c2756785378b0d0f5a1d73d3fca2`를 직접 확인했다.

## 0. 결론과 연구 등급

**이번에는 새로운 고속 실행기를 만들지 못했다.** 세 가지 표현을 구체적인 계산·비용
모형까지 내려 비교했고, 후보 B의 명시적 표에 대해 블록 크기를 섞어도 피할 수 없는
저장량 식을 유도했다. 후보 C의 독립 구간 인증에도 별도의 필요한 읽기 조건을 얻었다.
둘 다 특정 방식에 관한 결과다. VORTEX 전체의 불가능성 정리가 아니다.

앞선 소형 BDD 실험은 root 고정비가 지배해서 목표 규모의 속도 판단에 부적절했다.
이번 비용식은 작은 그래프 측정값을 외삽하지 않는다. 계수 수 N을 명시한 직접 계산이다.
이를 발견한 새 고속 알고리즘이나 목표 달성 가능성의 상승으로 계산하지 않는다.

`E0_ANALYTICAL_SCREEN`; 행렬/Transformer 백엔드나 전이 진리표는 만들지 않았다.
실행한 코드는 정수 비용 계산, 제한된 수치 증인, 증명 보조 검사뿐이다.

```
THEORY_STATUS=NOT_ESTABLISHED
CORE_ADMISSION=false
THREE_QUALIFYING_NEW_PRINCIPLES=false
HARDWARE_STATUS=NOT_TESTED
FULL_MISSION_O1_O6=OPEN
```

## 1. 최종 명제와 이번 질문

원본 체크포인트 W, 수치 ABI A, 합법적인 문맥/현재 입력 x, 상태 s, 난수 r에 대해
원본 전이 F(A,W,s,x,r)의 출력과 다음 상태·난수 사용을 보존하는 유한 자동 구성기와
인과적 실행기를 구성해야 한다. 원본 인터페이스가 logits를 노출하면 그것도 포함한다.
원본 보존, 재학습 없음, 단일 GPU 총 8 GiB, 같은 머신의 native 4B Q4 대비 warm
p50 <=1.2x, p95 <=1.5x 및 기존 TTFT 조건은 변경하지 않는다. 아직 미고정인
실제 ABI/지연 모집단을 임의의 유리한 설정으로 채워 성공을 선언하지 않는다.

이번 질문은 '현재 입력이 선택한 부분만 읽는 표현을 **작게 만들면서**, 그 부분의
실행 비용도 작게 만들 수 있는가'다. 10배 읽기 절감은 진입 관문이지 최종 지연 증명이 아니다.

## 2. 비교한 세 구성: 세 개의 새로운 완성 기술이라는 주장이 아님

| 후보 | 뒤집으려 한 전제와 계산 절차 | 10배 경로 및 먼저 확인할 항목 | 판정 |
|---|---|---|---|
| A: 수치 이동 관계로 부분 프로그램 공유 | 두 하위 함수가 같을 때만 공유하지 않고, `f_1(z)=f_0(z)+c`일 때 c를 경로에 적는다 | 코드 팽창을 억제하고 여러 계수의 작용을 짧은 이동으로 대체해야 함 | 가장 직접적인 affine decoder는 여전히 모든 비영 입력의 계수를 읽는다. 코드 축소만으로 채택하지 않음 |
| B: 원본 하위 계산 전체를 하나의 명령으로 | native reduction subtree를 한 개 입력 주소로 선택하는 정확한 표로 대체 | b개 항을 한 번 읽기로 바꾸되, 표 구성·저장·주소·cache를 포함 | 아래 고정 형식의 저장량 식에 의해 제외. 거대한 표를 실제 만들지 않음 |
| C: 분기를 저장하지 않고 가능한 결과 집합을 유지 | 읽지 않은 항을 구간으로 남기고 그 전체가 한 반올림 셀에 들어갈 때만 확정 | 적은 항만 확인해도 셀이 확정되어야 함 | 독립 부호 구간 모형의 합법적 하위 문제에서도 아래 필요조건에 막힘 |

A의 edge-valued 표현, B의 표 기반 부분 평가, C의 구간 검증에는 선행 개념이 있다.
관점을 바꾸려는 제안과 학술적으로 새롭다고 입증한 원리는 다르다. 세 후보가 모두
고정 목표의 적격 핵심 원리로 만들어진 것은 아니며, 기존 실패 계열을 이름만 바꿔
재승격하지 않는다. 새로 구성한 것은 아래의 **형식별 비용 연결과 검증 가능한 식**이다.

### A에서 코드가 작아져도 계산이 남는 이유

반올림 없는 합 f(b,z)=b*c+g(z)에서 b의 두 분기는 같은 g와 이동 c로 공유할 수 있다.
이를 반복하면 긴 분기표를 짧은 계수열로 저장할 수 있다. 하지만 직접 decoder
`sum_j w_j*x_j`는 x_j가 모두 비영이면 계수 payload를 그대로 전부 읽고 계산한다.
이 decoder의 읽기 비율은 1이다. 다른 모든 weighted-graph 실행기의 하한이 아니다.
FP32 중간 반올림이 있으면 이런 affine 관계도 자동으로 성립하지 않는다.
이 후보가 10배 관문에 들어가지 않는다는 계산 후 새 compiler를 만들지 않았다.

## 3. B의 정확한 계산 명세

native FP32 곱/덧셈의 순서가 고정된 트리를 생각하자. 원본 트리의 실제 하위 트리
b개 항을 하나로 잘라, 가능한 입력 조합마다 **그 하위 트리의 FP32 root 비트**를 저장한다.
질의 때 현재 b개 입력으로 주소를 만들고 그 비트를 읽는다. 위쪽 트리는 원본 그대로다.

모든 지원 조합이 저장되어 있고 수치 ABI가 정확히 같으면 귀납적으로 원본 root를
보존한다. 실수 결합법칙으로 덧셈 순서를 바꾸는 방식이 아니다. 이는 유한 알고리즘
명세이지, 이를 실제 원본 모델 전체에 만들었다는 주장이 아니다. 일반 GPU의 내부
트리가 이 예시와 같다고 가정하지 않는다. 입력 조합 이외에 외부 accumulator가 필요한
블록이면 그 상태도 인자로 들어가므로, 여기의 비용은 그런 방식보다 낙관적이다.

N개 BF16 계수를 b개씩 나누고, 각 입력 위치의 지원 값이 Q개, 저장 entry가 FP32
4바이트인 **비공유·비압축 직접 주소 표**를 정의한다. Q는 양자화하겠다는 제안이 아니다.
Q=2는 합법 입력 두 종류만 지원해도 이 형식이 얼마나 커지는지 보는 유리한 하위 모형이다.
유한 BF16 전체 비트 패턴을 그대로 구별하면 Q=65,280이다(부호 있는 0 포함).

이 고정 형식의 저장량 S와 cache 전 질의 entry payload R은:

    S = 4*(N/b)*Q^b bytes
    R = 4*(N/b) bytes
    원본 BF16 payload = 2N bytes
    rho = R/(2N) = 2/b
    S/(2N) = rho * Q^(2/rho)

주소 읽기·입력 인코딩·상위 덧셈·KV·원본 저장은 포함하지 않은 낙관적인 부분 비용이다.
빠른 주소 생성기를 공짜로 완성했다고 하지 않는다. 큰 b의 주소 자체도 여러 word다.

### 서로 다른 블록 크기를 섞으면?

블록 수를 K, 각 크기를 b_i>=1, 합을 N이라고 하자. R=4K, S=4*sum_i Q^b_i.
만약 a>=b+2인 두 크기가 있다면:

    Q^a + Q^b > Q^(a-1) + Q^(b+1), Q>=2.

따라서 총 항 수와 K를 고정할 때 크기가 최대 1만큼 다른 분할이 최솟값이다.
N=Kd+r (0<=r<K)이면 정확한 최솟값은:

    S_min = 4*((K-r)*Q^d + r*Q^(d+1)).

이 식은 행 경계와 native subtree 정렬 제약까지 풀어준 최솟값이다. 그 제약을 추가하면
최솟값이 더 작아지지는 않는다. 입력 적응형 압축·공유 표나 전혀 다른 decoder의
하한으로 확대해서는 안 된다.

### 직접 유도한 규모 예시

N=405,000,000,000, Q=2. 전 계수가 이 모형에 들어간다는 규모 예시이며 실제
405B layer 배치나 실행을 측정한 것이 아니다.

| b | cache 전 payload 비율 | 전체 표 바이트 | 의미 |
|---|---|---|---|
| 20 | 1/10 | 84,934,656,000,000,000 | 약 84.93 PB. 임의 20항 묶음을 허용한 낙관적 수치 |
| 32 | 1/16 | 217,432,719,360,000,000,000 | 약 217.43 EB. balanced subtree의 power-of-two 예 |

b=32의 질의 payload만 50,625,000,000바이트(50.625 GB)다. 이것을 원본 대비
16배 감소라고 할 수는 있지만 4B급 전체 지연을 달성했다고 말할 수 없다.
PB/EB는 십진 단위다. 준비 과정에서 이 표를 쓰는 바이트만 최소 S이며 그 비용을
장기 사용으로 무료화하지 않는다. 실제 표를 할당하거나 405B 가중치를 읽지 않았다.

### 8 GiB hot cache를 주면?

Q^b개 entry가 있는 같은 b의 표들을 생각하자. 현재 질의와 독립적으로 준비된 cache에
합계 H바이트가 들어 있고, 각 블록의 입력 조합이 Q^b개 중 균일하게 들어오는 진단
모형에서 기대 cold payload는 최소:

    max(0, R - H/Q^b).

각 cached entry가 선택될 확률이 1/Q^b이므로 기대값의 선형성으로 성립한다.
행 사이 질의의 독립성은 필요하지 않다. cache를 현재 질의에 맞춰 채웠다면 그 전송은
공짜가 아니며 이 모형에서 이미 준비된 hot cache로 세지 않는다. 표 사이의 alias/압축은
이 형식에 없고, 반복 질의가 몰리는 다른 분포에서는 이 식을 사용하지 않는다.

b=32, Q=2, H=8 GiB를 전부 표에 주어도 이 진단 모형에서 절약 가능한 기대량은
2바이트다. 이것은 실제 LLM 입력 분포나 p50/p95 측정이 아니다. 실제 장비에서는
KV와 다른 할당도 8 GiB를 나눠 써야 한다.

## 4. entry를 BF16으로 줄이면 되는가?

블록 FP32 root를 단순히 BF16으로 먼저 반올림하면 원본이 달라질 수 있다.
모든 개별 계수·입력이 BF16에 정확하게 들어가는 다음 두 계산을 비교했다.

    계수 = [256, 1, -256, 1]
    입력 A = [1, 1, 1, 0]
    입력 B = [1, 0, 1, 0]
    원본 트리 = BF16(RN32(RN32(p0+p1)+RN32(p2+p3)))

A의 왼쪽 FP32 root는 257, B는 256이다. 둘을 BF16에 저장하면 모두 256이다.
오른쪽 root는 둘 다 -256이다. 그러나 원본 최종 결과는 A=1, B=0이다.
따라서 BF16 값 하나만 남기는 이 대체는 틀린다. 모든 2바이트/부호화 상태가
불가능하다는 정보론적 명제가 아니다. 보정 정보나 원래 입력을 사용할 다른 decoder는
그 정보와 계산을 별도로 지불해야 한다.

`struct` 기반 FP32/BF16 비트 연산과 독립적인 유리수 ties-to-even 계산이 일치했다.
유리수 helper는 이 유한 정상 범위 증인용이며 IEEE 전체 구현이 아니다. Signed zero,
NaN, overflow, subnormal 전체가 검증됐다고 하지 않는다.

## 5. C: 가능한 구간만으로 일찍 확정하기 위한 필요조건

모든 곱이 +/-1이고 합계 n<2^24인 제한된 합법 native 하위 문제를 생각한다.
FP32 내부 합은 정확하고, 마지막에 precision p=8의 BF16 RNE를 적용한다.
k개 항의 실제 값을 확인한 합을 s라고 하자. |s|<=k다. 아직 확인하지 않은 n-k개
항의 부호를 독립적으로 +/-라고 두는 인증기는 R=n-k와 [s-R,s+R]를 유지한다.
두 끝점은 이 추상화에서 실제로 가능한 완료값이다.

RNE의 정상 범위 상대 오차 상한 u=2^-p를 적용한다. 같은 y로 반올림되려면:

    2R <= |s+R-y| + |y-(s-R)|
       <= u*(|s+R|+|s-R|)
        = 2u*max(|s|,R).

R>=|s|이고 R>0이면 u<1 때문에 불가능하다. 따라서 R<=u|s|<=uk이어야 한다.

    k >= ceil(n/(1+u)) = ceil(256n/257).

n=16,384이면 이 인증기는 최소 16,321개, 약 99.615%의 개별 항을 확인해야 한다.
특히 실제 항이 모두 +1인 경로에서는 endpoint 검사로 16,368개를 확인한 뒤 처음
확정된다. 구간은 비슷한 답의 허용범위가 아니라 **모든 가능한 완료값을 포함하는
정확성 증서**다. 입력을 대충 잘라낸 근사 추론 실험이 아니다.

**범위가 중요하다.** 이것은 '나머지 항을 독립 부호 구간으로만 남기는 항별 인증기'의
필요조건이다. 계수 전체의 부호가 이미 알려졌거나, 저렴한 집단 계산·popcount·공유
프로그램이 정보를 제공하면 이 모형과 다르다. 그런 다른 알고리즘의 가중치 읽기량,
HF 도달 상태, GPU 시간 또는 모든 exact certificate의 하한은 아니다.

## 6. 비용/의무 장부와 다음 작업

| 항목 | 이번에 한 일과 남은 의무 |
|---|---|
| O1 범용 자동 구성 | 일부 후보의 유한 명세만 있음; 자원 내 범용 생성기 없음. OPEN |
| O2 인과적 전체 실행 | 로딩/prefill/출력/후속 상태 전체 프로그램 없음. OPEN |
| O3 원본 숫자·상태·RNG | 잘린 subtree 교체의 조건부 귀납 관계와 작은 수치 증인뿐. OPEN |
| O4 전체 비용 | B 고정 형식의 S/R/cache/최소 쓰기량을 유도. 일반 decoder의 전체 상한 아님. OPEN |
| O5 실제 목표 예산 | 특정 후보의 큰 비용을 확인했으나 전체 목표를 닫지 못함. OPEN |
| O6 전체 해법의 검증 | 보조 유도식/코드만 재현. 전체 해법이 없으므로 전체 O6도 OPEN |

표 생성기의 지수적 저장·쓰기 비용, A의 남는 계수 연산, C의 항별 확인 문제를 안고
백엔드를 더 만들지는 않는다. 같은 BDD의 cap/order 확대도 하지 않았다.
여기서 '더 잘 압축하면 된다'는 말을 값싼 decoder로 취급해서는 안 된다.

다음 핵심 의무는 여전히 **표를 전부 물질화하지도, 개별 계수 계산으로 되돌아가지도
않으면서 현재 입력의 원본 출력·다음 상태를 만드는 구체적인 소스**다. 이번 비용식이
그 소스를 발명한 것은 아니다. 실패 보고를 늘리는 것을 우선 과제로 바꾸지 않는다.
이번 세 후보만 제외했고, 임무나 다른 비선형/적응적 부호화 전체를 제외하지 않았다.

## 7. 재현과 선행연구

```
python src/analyze.py --out regenerated_results
python -m unittest discover -s tests -v
```

사전등록은 결과 실행 전에 작성했다. 난수 씨드 탐색이나 성공 사례 선별은 없다.
21개 비용 사례, 5개 interval 폭, native 증인 두 경로를 모두 기록했다.
12개 로컬 검사는 비용식·분할 최소화·유리수 반올림의 무결성 검사다.
행렬곱 executor 검증 수, 공개 checkpoint 속도 또는 모델 정확도처럼 보고하지 않는다.

2026-09-06 조회한 1차 자료:

- Tafertshofer & Pedram, *Factored Edge-Valued Binary Decision Diagrams* (1997).
  https://link.springer.com/article/10.1023/A:1008691605584
  additive/multiplicative edge로 함수 표현을 공유하는 선행 개념. 임의 BF16 LLM 전체의
  크기·질의 예산 보장이 아니며 이번에 새로 발명했다고 하지 않는다.
- NVIDIA, *Floating Point and IEEE 754*.
  https://docs.nvidia.com/cuda/floating-point/index.html
  반올림, 계산 순서 및 dot product 구현 구분의 근거. 이번 native 증인의 기준을 실제
  CUDA 커널 전체와 같다고 확대하지 않는다.
- Ferragina et al., *Improving Matrix-vector Multiplication via Lossless Grammar-Compressed
  Matrices* (2022). https://arxiv.org/abs/2203.14540
  압축 표현에서 행렬곱하는 실제 선행연구. B의 비공유 직접 표 비용식은 이런 다른
  압축표현의 하한이 아니다. 이번에 이 논문 구현을 재현하지 않았다.

원격 기록은 SHA와 변경 파일을 읽어 확인한 뒤 별도로 보고한다. 기록 완료는
새 알고리즘 완성이나 성능 목표 달성과 별개다. 이전 ZIP들은 문맥일 뿐 이번 커밋에
소급 편입하지 않는다. main 직접 쓰기/force push/병합/Actions dispatch는 하지 않는다.
