# VORTEX: 출력 구간 공동화와 원본 공개 가중치 검사

날짜: 2026-09-08. 부모: PR #146, `66c01825635a357f86f9dfa5369088d7a239c92d`.

## 1. 무엇을 구성했나

가중치가 다른 여러 행도 **최종 BF16 출력이 정확히 같다는 사실을 먼저
증명**할 수 있으면, 행마다 곱셈을 수행하지 않고 같은 출력을 기록하는
조건부 실행기를 구성했다. 입력에 필요한 정보를 알려주는 외부 선택기,
이전 입력의 유사성, 가능한 입력별 정답표를 사용하지 않는다.

결정적인 비용 조건을 실제 공개 가중치로 검사했다. 고정한 행 묶음에서는
432개 질의-묶음 모두 출력이 서로 달랐다. 따라서 이번 형식은 이 자료에서
더 정밀한 인증기를 부착해도 행 묶음을 하나의 출력으로 대체할 수 없다.
원본 가중치 읽기100%, 추가 구간 계산이 남는다. 이 결과는 범용 알고리즘의
불가능성이나, 이 모델의 실제 생성 문맥 전체에 대한 결론이 아니다.

**THEORY_STATUS=NOT_ESTABLISHED; HARDWARE_STATUS=NOT_TESTED;
CORE_ADMISSION=false; FULL_MISSION_O1_O6=OPEN.**

## 2. 고정 목표와 선택한 연구 범위

임의의 공개·미수정 HF dense405B, batch1, 단일 GPU 전체 <=8GiB,
원본 출력/RNG/필요한 다음 상태, 같은 머신의 native4BQ4 대비
p50<=1.2x,p95<=1.5x와 기존 TTFT 목표는 그대로다. 이 문서는 그 목표를
달성한 이론이 아니라, O3 수치 연결의 제한된 구성과 O4 비용 검사를 기록한다.

사전등록에서 비교한 세 정보 흐름은 A 출력 공동화, B 출력 차이의 압축된
native 보정, C 지연된 문맥 상태의 공동 전이다. B의 저렴한 보정 정보원과
C의 제한된 누적 forcing 비용은 미구성이다. A만 작은 공개 가중치 검사까지
구성했다. 기존 구간·공동화 도구를 썼으며 **새 범용 원리 세 개를 발명하거나
10배 경로를 입증했다는 주장이 아니다.**

## 3. 정확한 생성·실행 절차

원래 기준 계산은 유한 BF16 가중치와 입력을 정확히 FP32로 확장한 후,
각 곱을 별도로 FP32 RNE로 계산하고, 다음2의거듭제곱까지 +0패딩한
균형 덧셈 트리를 FP32 RNE로 평가한 뒤 최종 BF16 RNE로 저장한다.
출력 NaN은 양의 canonical NaN으로 고정한다. 입력NaN/무한대는 범위 밖이다.
**이 ABI는 실제 HF/CUDA 커널의 ABI를 검증한 것이 아니다.**

행들을 원래 순서의 최대256개 묶음 P로 나눈다. 생성기는 모든 원본 값을
읽고 각 입력 좌표j의 정확한 최솟값 l_j와 최댓값 h_j를 저장한다.

현재 x에서 x_j>=0이면 곱의 하한/상한은 RN32(l_j*x_j),RN32(h_j*x_j),
x_j<0이면 두 가중치를 바꾼 값이다. 두 끝점 배열을 원래와 동일한 트리로
각각 더한다. 이 과정의 모든 중간값이 유한하고, 최종 양 끝점을 BF16으로
반올림한 값이 같은 **0 아닌 유한 비트값**이면 그 값을 P 전체에 기록한다.
그렇지 않으면 저장된 원본 파일에서 P의 행들을 실제로 읽고 직접 계산한다.
현재 입력의 모든 성분은 읽는다. 생략 대상은 입력이 아니라 해당 원본
가중치 행들의 읽기와 곱셈·덧셈이다.

실행 객체에는 원본 전체 배열을 넣지 않지만, 거부된 묶음에서는 reader가
원본 파일을 읽는다. 시험 드라이버는 별도 참조 검증용 원본 배열을 보유한다.
OS가 파일을 캐시할 수 있으므로 실제 SSD/PCIe 트래픽을 측정했다고 하지 않는다.

## 4. 정확성·종료 증명

유한 구간에서 IEEE RNE 곱셈은 곱하는 고정 입력의 부호에 맞춰 단조이고,
덧셈과 최종 RNE 변환은 수치 순서를 보존한다. 그러므로 각 원본 곱은 두
끝점 사이에 있고, 트리의 같은 자식을 더하는 귀납으로 각 중간값도 그
구간 안에 있다. 모든 끝점 중간값의 유한성을 검사하므로 인증 경로 안에서
미확인 NaN/overflow로 순서 관계가 깨지는 일을 허용하지 않는다.

최종 양 끝점이 같은 0 아닌 BF16 값으로 반올림되면, 그 사이의 모든
원본 FP32 결과는 같은 BF16 비트로 저장된다. signed zero는 수치 순서만으로
비트를 확정할 수 없으므로 0 singleton은 직접 계산한다. 불확실한 경우에는
원래 행을 같은 명령·순서로 평가하여 전체 출력을 반환한다. 유한 개의
묶음과 유한 트리이므로 종료한다. FP32 중간 결과 자체를 동일하게 반환하는
API나 FP예외 플래그는 계약에 포함하지 않는다.

이 연산을 전체 실행에 대입하려면 실제 projection ABI 일치, observer의
BF16 저장 경계, 전체 상태 전이·난수 소비 대응을 추가로 증명해야 한다.
이번 연구에서는 Transformer를 대체하지 않았고 KV/RNG induction은 OPEN이다.

## 5. 실제 공개 가중치·입력 출처

모델: `HuggingFaceTB/SmolLM2-135M`.
고정 revision: `93efa2f097d58c2a74874c7e644dbc9b0cee75a2`.
층0/15/29의 q_proj,gate_proj,up_proj,down_proj 전체 행렬12개다.
가중치 dtype은 원본 BF16 그대로다. 값을 바꾸거나 다시 양자화하지 않았다.

먼저 공개 메타데이터를 확인하고 사전등록을 작성했으며, run.py는 원본
숫자 payload를 열기 전에 소스/사전등록 해시를 기록했다. safetensors의
8바이트 길이와 JSON 헤더, 지정된12텐서 영역만 HTTP Range로 읽었다.
14응답 모두206과 정확한 Content-Range/길이를 검사했다. 수신 payload는
17,946,440바이트이며 원본 텐서 숫자는17,915,904바이트다. 모델 전체
269,060,552바이트 파일을 다운로드한 것이 아니다. 원본 텐서별 SHA256은
weight_manifest.json에 보존한다. 원본 가중치는 Git에 넣지 않는다.

행렬마다 NumPy PCG64 seed260908 정규분포8입력을 BF16 RNE로 만든다.
**실제 사전학습 가중치 + 합성 입력**의 검사다. 실제 문장을 HF 모델에
통과시킨 activation trace가 아니며, 실제 도달 상태에 대한 결론은 유보한다.
입력 크기가 같으면 같은 생성 배열을 사용한다. 결과 후 층·입력·묶음 순서를
선택하거나 조정하지 않았다.

128배 실제 가속이나 공개 모델 성과가 아니다. 이 대조군은 따로 집계했다.

## 7. 비용 판정

m행,n열,g=ceil(m/b), 인증한 행c라면 원본2mn바이트 대비 질의 계수량은
4gn+2(m-c)n바이트다. 곱셈과 패딩트리 덧셈의 개수는
(2g+m-c)*(n+nextpow2(n)-1)이다. min/max의 sign선택, 유한성·비트비교,
입력변환, 출력기록, 배열할당·중간읽기쓰기, 파일주소·헤더는 추가다.

m이b로 나누어지면 두 비율 모두 2/b+1-f (f=c/m)다. b256에서10배 감소를
얻으려면 다른 비용을 빼고도 f>=90.78125%가 필요하다. 실제 f=0이다.
각 행렬은 원본 계수량/FP연산의100.78125%~101.04167%를 사용했다.

원본12텐서 합17,915,904B에 구간payload158,976B를 더해, 가중치 관련
질의 바이트만의 가중평균도 증가했다. results/costs.json은 정확한 비율과
준비+8질의 예를 계산한다. 단순 범용 규모 예시로4050억 계수·완전256행
묶음을 가정하면 구간payload만6,328,125,000B(약5.89GiB)이고 원본810GB는
따로 남는다. 이 수치는 실제405B 구조를 측정하거나 모델을5.89GiB로
압축했다는 뜻이 아니다.

현 생성기는 원본과 FP32 복사본을 보유하므로 O(mn) host 메모리를 쓴다.
질의 배열은 O(gn+b*nextpow2(n)+m+n)이고 OS캐시·할당자 등은 추가다.
전체8GiB GPU memory나 상주·cold 시간, baseline p50/p95를 측정하지 않았다.
음의 결과가 명확하므로 큰 GPU 백엔드나 같은 parameter sweep을 진행하지 않는다.

## 8. 왜 인증기를 정교하게 하는 것으로 끝나지 않나

참조 출력이 서로 다른 행들을 하나의 같은 값으로 반환하는 일은 불가능하다.
432묶음 모두 이런 경우였다. 참조값을 본 완벽한 선택기도 이 고정 broadcast
형식에서는0묶음만 생략할 수 있다. 이 oracle은 실행기에 전달하지 않고
사후의 형식별 상한으로만 썼다. 다른 묶음 선택, 서로 다른 값들을 공동
생성하는 계산법, 실제 문맥의 다른 입력, 전체 모델에 대한 하한은 아니다.

결정적인 다음 정보원은 **서로 다른 출력의 정확한 효과도 공동으로 생성**해야
한다. 단순히 같은 값으로 합치거나, 그 차이를 원본 계산으로 다시 구하는
방식은 이번 비용 문제를 해결하지 않는다. 이 문서는 그 새 생성기를 제공하지 않는다.

## 9. 재현·원격 보존

원본 가중치는 .cache에만 보관한다. 구간 .npz도 원본 일부 계수에서 유래하므로
Git에는 넣지 않고, 해시·생성 코드로 재생성한다. 입력 .npy, 후보/참조 출력,
묶음별 구간비트·주소/읽기 기록, 공개 텐서 hash, HTTP 응답 영수증, 초기소스hash,
단위검사·재생성로그는 보존한다. 코드는 Python3.12.10/NumPy 환경에서 실행했다.

실행: `py -3.12 run.py --output replay/fresh` (새 폴더 사용).
검사: `py -3.12 verify.py --rerun` (최초 로컬 science와 weights cache가 있을 때).
Git에서 새로 받을 때의 검사는 README의 portable_replay 절차를 따른다.
네트워크 재취득은 같은 revision·tensor SHA256와 비교해야 하며, 변경되면 실패한다.

12개 단위검사와 원래39개 scientific 파일의 hash검사가 통과했고,
새 폴더로 전체 계산을 다시 생성해 결과가 같았다. 환경·타이밍진단은
고정해시 대상에서 제외한다. run.py는 획득·준비 시간을 기록하지만 후보vs기준의
성능 벤치마크가 아니므로 latency 주장을 하지 않는다.

상태/입력/숫자 경계 검사는 source/tests에 있다. 전체 저장소 suite,
HF forward, 실제KV/RNG, CUDA,405B,8GiB,4BQ4/TTFT는 NOT_TESTED다.
영속화의 완료와 과학적 목표 달성은 별개다. 최종 commit/PR/readback은
후속 인계 영수증으로 기록하며 자기 자신을 포함하는 commit SHA를 만들지 않는다.
