# 표준 SwiGLU·Attention 전체 연산의 표현 변경과 비용 검증

2026-09-06. 이 기록은 **범위가 제한된 구성·검증 결과**다. 세 표현을 직접 식과 프로그램으로 구성했지만, 새로운 핵심 실행 원리 세 가지나 10배 이상 절감 경로를 확보한 회차로 인정하지 않는다. 전체 목표와 O1–O6는 OPEN이다.

## 1. 목표, 범위, 이전 연구와의 차이

목표는 임의의 공개·미수정 HF dense 405B급 모델, 배치 1, 단일 GPU 전체 8GiB 이하, 원본 출력·RNG·필요한 다음 상태 보존, 같은 머신 native 4B Q4 대비 p50 ≤1.2배/p95 ≤1.5배와 기존 TTFT 조건이다. 전처리·CPU/RAM/SSD/전송·상태·검증·복구를 모두 계상한다.

직전 번들의 SiLU 대칭차 보정은 원본 LlamaMLP에 없는 대칭 분기가 필요했고, 입력을 만드는 행렬곱을 제거하지 못했다. 이번에는 원본의 bias-free SwiGLU 식 `F(x)=D[SiLU(Gx) ⊙ Ux]`와 projected-key attention의 연산 순서 자체를 대상으로 했다. 이 식의 범위는 bias-free 블록이며, 이를 모든 HF 모델로 몰래 확대하지 않는다.

이번에는 (A) 블록 전체의 짝수/홀수 분해, (B) 가중치의 정확한 이진 유리수 표현을 이용한 지수 단항식 프로그램, (C) key 생성 대신 query를 과거 hidden 방향으로 옮기는 실행을 비교했다. A는 이전 대칭 연구의 확장이고 C는 알려진 쌍대성이다. B도 지수의 준동형 관계를 이용한다. **세 개의 학계 최초 원리나 CTC를 통과한 새 core 세 개를 발명했다고 주장하지 않는다.** 조건을 충족하지 않은 후보를 이름만 바꿔 승격하지 않는다.

현재 원격 기준은 PR #127의 `cfb28c0a803ce16e9eaf6fbefab0ad40a8aa0c76`이다. 별도의 `research/rounding-residue-compiler-20260906` 브랜치도 조회했으나 head는 이전 정책 커밋 `04ca65be174bf63b327666b63ea6afca51bde938`였고, 새 연구가 커밋된 증거로 취급하지 않았다. 이전 두 로컬 번들은 맥락으로만 읽었으며 이 코드에 몰래 병합하지 않았다.

## 3. A — 블록 전체의 2차식 부분을 미리 계산하기

`g=Gx`, `u=Ux`로 쓰자. 실수에서

\[
\operatorname{SiLU}(z)=\frac z2+\frac z2\tanh(z/2)
\]

이므로

\[
\boxed{F(x)=\tfrac12 B(x)+\tfrac12 H(x)}
\]

\[
B(x)=D[(Gx)\odot(Ux)],\qquad
H(x)=D[(Gx)\odot(Ux)\odot\tanh(Gx/2)].
\]

`B`는 짝수 함수, `H`는 홀수 함수다. 따라서 실수 연산에 한해 `F(x)+F(-x)=B(x)`이다. 새로운 반사 분기를 원본 그래프에 넣어 공짜로 실행한다는 뜻이 아니라, 원본 블록의 정보를 두 성분으로 나눈 분석이다.

### 유한한 정확한 2차식 생성기

입력 폭 n, 중간 폭 f, 출력 폭 m에서 j≤k인 계수를 다음처럼 직접 만든다.

\[
C_{o,jj}=\sum_iD_{oi}G_{ij}U_{ij},
\]
\[
C_{o,jk}=\sum_iD_{oi}(G_{ij}U_{ik}+G_{ik}U_{ij})\quad(j<k).
\]

그 결과 `B_o(x)=Σ_{j≤k} C_{o,jk} x_j x_k`이다. `compile_quadratic`는 Python Fraction으로 실제 계수를 생성한다. 생성은 유한한 삼중/사중 반복이고, 각 유리수를 정확하게 곱하고 더한다. 직접 전개와 생성된 식을 사전등록된 125개 입력·2개 출력, 총 250개 결과에서 비교해 불일치가 없었다. 일반적인 대수적 정확성은 분배법칙으로 증명되며, 250개 시험에서 추정한 것이 아니다.

모든 유한 BF16은 `a·2^-133`, `|a|<2^261`로 쓸 수 있다. 위 계수는 공통 분모 `2^399`를 가진 정수 합으로 표현 가능하다. n과 무관하게 분자 절댓값은 off-diagonal에서 `2f·2^783` 미만이므로 부호를 포함해 `785+ceil(log2 f)`비트면 충분하다. f=53,248이면 801비트의 고정 폭은 충분조건이다. 모든 계수가 이 폭을 실제로 필요로 한다는 하한은 아니다. 이는 정확한 생성·저장의 한 유한 상한일 뿐, 목표 예산을 충족하는 상한이 아니다.

### 2차식이 0이어도 원래 블록은 없어지지 않는다

코드에는 다음처럼 모든 가중치가 0이 아니며 G와 U 모두 열 rank가 2인 블록을 넣었다.

```text
G = [[1,1], [1,-1], [1,2], [1,-2]]
U = [[2,2], [4,-4], [8,16], [16,-32]]
D = [[-1, 1/2, 1/8, -1/16]]
x = [1,2]
```

컴파일된 2차 계수는 정확히 `[0,0,0]`이다. 그러나 선언한 BF16 기준에서 원본 출력은 **7.875**, 반대 입력의 출력은 **-7.78125**였다. 따라서 2차식만 남기면 틀리고, 실수의 parity 관계도 native 실행에 그대로 쓰면 틀린다. 이것은 특별히 쉬운 양성 예를 목표 성과로 삼은 것이 아니라, 제안한 소거 규칙을 반박하는 명시적 표준 블록이다.

더 일반적으로 실수에서 x=t v로 제한하면, 서로 다른 양의 `a_i^2=(G_i v)^2`에 대한 홀수 Taylor 계수에는 `Σ_i c_i b_i a_i^(2k)`가 들어간다. 처음 f개의 이러한 계수가 모두 0이면 Vandermonde 계의 가역성 때문에 각 `c_i b_i a_i^2`가 0이어야 한다. 이 조건에서 일반적인 비선형 성분은 2차식으로 사라지지 않는다. 이는 실수의 제한된 구조 명제이지 원본 유한 워드 회로나 모든 VORTEX 실행기에 대한 하한이 아니다.

### 저장과 남은 실행 비용

전처리는 원본 G/U/D 전체를 읽고, 선언한 구현의 산술 횟수는 보수적으로 `3mfn²` 곱셈 이하와 같은 차수의 덧셈이다. 정확한 정수/유리수 연산의 비트 비용도 추가된다. 한 번의 tensor query는 n(n+1)/2개 입력 곱과 m n(n+1)/2개 계수 곱, 그에 상응하는 덧셈·읽기가 필요하다.

대형 **규모 예시** n=m=16,384, f=53,248에서 계수 개수는 2,199,157,473,280개다. 각 계수를 2바이트에 넣는 낙관적인 균일 배열을 가정해도 **4,096.25GiB**다. 원래 세 projection의 BF16 payload는 **4.875GiB**다. 이는 실제 다운로드한 405B 체크포인트 측정이 아니며, 모든 압축·인수분해 표현에 대한 하한도 아니다. 정확한 일반 계수가 BF16 한 개로 저장된다고 주장하지 않는다.

더 중요하게, H를 위 식 그대로 실행하면 G/U/D의 원래 projection 읽기 **100%**가 그대로 필요하다. 따라서 2차식을 컴파일했다는 사실만으로 10배 절감 경로가 생기지 않는다. 미정의 저렴한 H 계산기를 성공 조건으로 넣지 않았고, 이 후보를 확장하지 않았다.

## 4. B — 덧셈 대신 지수의 곱으로 전체 projection 전달하기

각 열의 정확한 2의 거듭제곱 공통 분모를 고르면 `W_ij=2^-q_j A_ij`인 정수 A를 만들 수 있다. 실수에서는

\[
z_j=\exp(2^{-q_j}x_j),\qquad
\exp((Wx)_i)=\prod_j z_j^{A_{ij}}.
\]

이 표현은 입력 재사용이나 가중치 저랭크를 가정하지 않는다. 각 입력에서 z_j를 만들고, 공유된 반복 제곱들 `z_j^(2^b)`를 만든 다음, 행마다 미리 기록한 양수·음수 지수의 bit 위치를 읽어 곱하고 나눈다. `log`로 projection을 다시 얻거나 sigmoid의 odds로 사용한다. `compile_monomials`, `monomial_projection`에 유한한 절차가 전부 있다. exp/log가 무료이거나 native 덧셈과 같다고 가정하지 않는다.

BF16 유한 가중치의 절댓값 정수 A에는 유효 1비트가 최대 8개 있고, 열별 최대 길이는 261비트 이하이다. 따라서 직접 생성한 프로그램은 최대 8mn개 power 참조와 261n개 shared power를 사용한다. 이것은 유한한 코드·작업량 상한이다. 작은 회로가 반드시 발견된다는 가정은 없지만, 이 상한은 목표 절감과 반대 방향이다. 실제 FP64 구현에는 overflow/cancellation도 가능하며, 발생하면 명시적으로 오류를 반환한다. 오류를 원본 fallback으로 숨기지 않는다.

### 실제 저장 형식과 비용

VMP1 직렬화는 16바이트 헤더, 열별 shift/length, 행별 양·음 참조 offset과 실제 power index들을 저장한다. 생성한 바이트열을 다시 해석한 프로그램으로도 동일한 query를 수행했다. 가중치 16×8=128개, 원본 256바이트인 네 사례에서:

| 항목 | 결과 |
|---|---:|
| 실제 직렬화된 gate 프로그램 | 1,284–1,306바이트 |
| 공통 FP64 power 작업 공간 | 800–896바이트 |
| 반복제곱/행 곱셈 | 610–626회 |
| 원본 gate 곱셈 | 128회 |
| 추가 함수 | exp 8회, log 16회, 나눗셈 16회 |

여기에 원본 up/down, 입력·출력, 프로그램 해석·주소 처리, Python 객체 비용이 남는다. 위 byte 수는 실제 이진 프로그램 payload와 명시한 수치 작업 배열이며 Python 프로세스 전체 메모리나 GPU VRAM 측정은 아니다. 곱셈 횟수 비율을 실행시간 비율로 바꾸지 않는다. 256바이트를 보존하고 실행하는 다른 동등 구현은 가능하지만, 그 경우 원본 가중치 읽기를 없앤 것이 아니다.

### native 동등성

실수 projection의 반올림을 없애고 SiLU까지 전달하는 변형은 512개 출력 중 **232개**에서 달랐다. 중간 BF16 gate를 다시 저장한 변형은 같은 작은 표본에서는 **0/512**였지만, 그것을 원본 FP32 reduction 전체의 등가성 증명으로 승격하지 않는다.

명시적 반례가 있다. `G=[1,1/256]`, x=[1,1]의 실수 projection은 257/256이지만 원본 BF16 gate는 1이다. 원본 SiLU 출력은 0.73046875, projection 저장을 건너뛴 변형은 0.734375였다.

더 강하게 `W=[2^24,1,-2^24,1]`, x=[1,1,1,1]에서 원본 balanced FP32 reduction 후 BF16은 1이지만, 정확한 실수 합은 2다. 따라서 완벽한 실수 복원 뒤에 BF16로 한 번 반올림해도 native가 자동 복원되지 않는다. 유리수 RNE 검사로도 이 차이를 독립 확인했다. 이 반례가 모든 정밀도 알고리즘을 금지하는 것은 아니다. 미해결 native 보정 비용을 숨기는 이 직접 확장만 거부한다.

## 5. C — projected key 대신 query를 hidden 방향으로 옮기기

실수에서 `qᵀ(W_K h)=(W_Kᵀq)ᵀh`이므로, 매번 K를 만들지 않고 과거 h를 보존하는 방법을 검토했다. 하지만 원본은 `RN_bf16(W_K h)`를 저장한다.

```text
W_K=[[1,1],[1,2]], q=[2,-1]
history=[[0,0],[1,256]]
```

원본 두 key는 [0,0]과 [256,512]이고 두 score는 [0,0]이다. 옮긴 query는 [1,0]이고 옮긴 score는 [0,1]이다. sqrt(2) scaling, FP32 softmax 후 BF16, value [0,1]까지 수행하면 attention 출력이 **0.5 → 0.66796875**로 달라졌다. 단순 점수 차이로 끝내지 않고 소비자 출력까지 확인했다. RoPE·KV 전체 관리·RNG·완전한 HF decoder를 검사한 것은 아니다.

한 head의 원래 key 폭을 k, hidden 폭을 d라 하면, key history는 Tk워드인데 hidden history는 Td워드다. 현재 key 생성 dk 연산을 없애도 각 새 query의 pullback에 dk 연산이 다시 필요하고, attention history 읽기는 Tk에서 Td로 커진다. 예시 d=16,384, k=128에서는 한 head 기준 history 항이 128배다. 여러 head 간 hidden 공유/GQA를 포함한 전체 메모리 비율로 이를 확대하지 않는다. 전체 모델은 그 공유 비용을 따로 세야 한다. 원본 key와 재구축 비용을 함께 보존하면 무료 저장 절감이 아니다.

## 6. 검증 수준과 판정

4개 합성 블록, 64개 독립 입력, 512개 출력 워드에서 검사했다. 실수 식의 FP64 검산 최대 절대 차이는 8.89e-16 미만이었지만 이는 실수 정리의 증명이 아니라 수치 확인이다. 무보정 짝수/홀수 native 치환은 **309/512**에서 달랐다. 모든 통계는 해당 고정 합성 집단에 한정된다.

12개 단위 검사가 통과했다. 독립 Fraction RNE, exact quadratic compiler, 원본 계수 비트 표현, packed program round-trip, 손상 payload 거부, 비용식, 상태 승격 금지를 검사한다. summary/raw/environment/serialized program 4개 파일은 재실행 후 바이트 단위로 일치했다. **후보가 빠른 실행기로 통과했다는 12개 시험이 아니다.** 실패하는 치환을 실패로 검출하는 시험도 포함되어 있다.

```text
FULL_MISSION_O1_O6=OPEN
```

기존 목표의 물리적 불가능성이나 모든 새로운 계산 원리의 부재를 증명한 것은 아니다. 그러나 이번 세 경로를 핵심 엔진 진척으로 보고할 근거도 없다. 2차식 생성, 지수 프로그램, query pullback에 더 큰 백엔드나 대형 체크포인트 실행을 붙이지 않는다. 현재 핵심 의무는 **원본의 비선형·반올림 동작을 보존하면서 대부분의 계수 작업을 하지 않는 저비용 정보 생성 절차**다. 기존 원격 NEXT_EXPERIMENT를 새로운 표/반례 수집으로 대체하지 않는다.

## 7. 재현과 출처

동일 CPU 환경(torch 2.10.0+cpu, numpy 2.3.5)에서 번들 루트를 기준으로:

```bash
python src/research.py --out results
python -m unittest discover -s tests -v
```

- 원시 입력/출력: `results/raw.jsonl`
- 실제 VMP1 바이트열(base64), 길이, SHA-256: `results/serialized_programs.json`
- 환경/요약/검증: `results/environment.json`, `results/summary.json`, `results/validation.json`
- 코드/단위 검사: `src/research.py`, `tests/test_research.py`
- frozen 가설/크기/seed: `PREREGISTRATION.json`

공식 정의와 native 주의사항을 확인한 출처(2026-09-06 조회):

- https://arxiv.org/abs/2002.05202 — GLU variants 원논문. 이번 변형의 목표 성능 증거는 아니다.
- https://github.com/huggingface/transformers/blob/main/src/transformers/models/llama/modeling_llama.py — 실제 `down_proj(act_fn(gate_proj(x))*up_proj(x))`와 eager attention의 FP32 softmax/BF16 저장. 소스 확인과 실제 공개 모델 실행을 구분한다.
- https://docs.nvidia.com/cuda/floating-point/index.html — reduction/FMA/반올림 및 고정밀 계산 후 cast와 원본 실행의 차이.

위 식 전개, 생성기, 비용, 구체 반례와 수치는 이 연구의 산출물이다. 수학적 기초 관계나 표준 표현을 최초 발명이라고 주장하지 않는다. 성능·전처리 적합성·완전한 state/RNG·CUDA에 대해서는 측정하지 않은 수치를 제시하지 않는다.
